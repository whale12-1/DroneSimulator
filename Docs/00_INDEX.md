## 1. Что это за документ

Это «чистая» база знаний по игровому проекту DroneSimulator, собранная **заново с нуля** по фактическому состоянию ассетов и кода (а не по прежним заметкам).
Старая документация в `Docs/` удалена полностью (включая `ARCHITECTURE.md`, `CONTEXT.md`, `INDEX.md`, `SETTINGS_DESIGN.md`, `MissionSelectScreen_preview.png`, `PlayerAnimator.controller.bak`).

Область анализа сознательно ограничена пятью сценами игрового цикла. Все прочие сцены (`SampleScene`, `TerrainDemoScene`, `player`, `FunctionalUI-Demo`, `FirstMission(SpizjenyiVaarik)`) в аудит **не входят** — они помечены как «вне области» и предназначены к удалению позже.

## 3. Краткая карта проекта (TL;DR)

```
Boot ──► MainMenu ──► Bunker(main) ──► PreparingDemo ──► Debrief ─┐
                            ▲                (обучение)           │
                            │                                    │
                            └──────────── Debrief ◄───────────────┤
                                             ▲                   │
                                             │                   │
                                  FirstMission(Forest) ◄──────────┘
                                     (засада БТР/РСЗО)
```

* `Boot` — техническая сцена-загрузчик: поднимает `SceneLoader` и `SettingsService`, уводит в `MainMenu`.
* `MainMenu` — главное меню (видео-фон, Play/Settings/Exit).
* `Bunker(main)` — «хаб»: вид от первого лица, сесть за терминал, выбрать миссию на «рабочем столе» ОС.
* `PreparingDemo` — обучающая миссия (3 главы) на ударном/разведывательном дроне.
* `FirstMission(Forest)` — боевая миссия-засада: уничтожить БТР прикрытия, затем догнать и уничтожить РСЗО.
* `Debrief` — не отдельная сцена, а **состояние FSM** внутри игровой сцены: панель результата + возврат в Bunker.

## 4. Как читать базу знаний

1. Начните с `01_GAME_ARCHITECTURE.md` — там описан каркас (FSM + сервисы + сохранения).
2. Дальше — `02_SCENES_OVERVIEW.md` по нужной сцене.
3. Для правок кода — `03_CORE_SCRIPTS.md` (карта зависимостей) и `04_PREFABS_AND_UI.md` (если затрагивается UI).
4. Перед постановкой задач — `05_CURRENT_STATE.md` (там же список технического долга с точными ссылками `файл:строка`).

## 5. Методика сбора контекста (чтобы можно было повторить)

Документация построена на фактическом графе зависимостей, а не на догадках:

1. Для каждой сцены `.unity` извлечены **все GUID** (`guid: <32 hex>`), а также привязки `m_Script` → `m_GameObject` → `m_Name`.
2. Все 3086 файлов `.meta` в `Assets/` преобразованы в карту `GUID → путь ассета`.
3. GUID из сцен развёрнуты в конкретные `.cs`, `.prefab`, `.asset`, `.mat`, `.controller`, `.fbx`.
4. Для префабов выполнена **рекурсия второго уровня** (префаб → вложенные префабы → их скрипты).
5. Код прочитан целиком по всем скриптам, привязанным к сценам и к префабам из этих сцен.
6. Отдельно проверены `ProjectSettings` (`EditorBuildSettings`, `ProjectVersion`, `activeInputHandler`), `Resources/MissionRegistry.asset` и `Resources/Missions/*.asset`.

## 6. Ограничения этой базы знаний

* Описано **только то, что реально привязано** к 5 сценам (напрямую или через префабы этих сцен).
* Скрипты, существующие в проекте, но не используемые в этих сценах, перечислены в `05_CURRENT_STATE.md` как «мёртвый/недостижимый код» — они не расписаны детально.
* Настройки сцен (позиции объектов, конкретные материалы интерьера бункера) не документировались — только структура и логика.
* Значения полей в инспекторе приводятся только там, где они влияют на поведение (например `MissionController.autoComplete`).
